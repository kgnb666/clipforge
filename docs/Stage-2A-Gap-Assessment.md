## 3. 架构调查（§三问题 1–2）

1. **验证在哪一层**：纯 Rust 层。`create_import_entry` 命令（`import.rs:220`）→ `ImportState::create_entry`（`import.rs:100`，互斥锁内判重）→ `comparison_key`（`import.rs:200`，canonicalize/大小写折叠判重键）→ `build_entry`（`import.rs:136`）→ `validate_readable_file`（`import.rs:165-195`）：空→`INVALID_PATH`；`!exists()`→`NOT_FOUND`（:170-176）；`!is_file()`→`NOT_A_FILE`（:177-179）；`File::open` 失败→`PermissionDenied`→`PERMISSION_DENIED`（:180-186）或 `ACCESS_FAILED`（含 OS 错误号，:187-193）。**不读取媒体元数据**（FFprobe 属 Phase 2B）；仅只读打开一次验证可读性。
2. **错误如何传递与展示**：命令返回 `CreateImportResult { outcome, entry }`（camelCase）→ 前端 `importApi.ts` 的类型化包装 → `App.tsx` 在刷新列表后按 `entry.status` 渲染：成功徽标"已导入（路径校验通过）"；失败徽标"导入失败"+ `<div class="entry-error">{errorMessage}（{errorCode}）</div>`（`App.tsx:97-98`）；重复路径 → 顶部提示"已在列表中"（`App.tsx:49`）；对话框取消 → `pick_video_file` 返回 `Ok(None)`（`picker.rs:16`）→ 无条目无报错（`App.tsx:41`）；命令异常 → catch → 提示 `导入失败：…`（全局兜底，不吞错）。

## 4. 失败场景可测试入口调查（§三问题 3–7）

### 4.1 现有可复用机制（问题 3）

- Rust 单元测试 9 个（直调 `ImportState::create_entry`，与命令同一逻辑）——**逻辑级已充分**，不需要扩充为覆盖 UI。
- UI 自动化：`gate2a-ui-helper.ps1`（UIA 驱动真实对话框/截图/读取界面文本）——已验证可用。
- **无**运行态"命令级"测试入口：`invoke_handler` 仅暴露 `greet`、`create_import_entry`、`list_import_entries`、`pick_video_file`（`lib.rs:18-22`），无测试命令、无测试替身、无集成测试框架（`tauri::test/mock_builder` 未被使用——若用只能覆盖命令与逻辑，覆盖不到 UI 渲染，非本缺口所需）。

### 4.2 绕过对话框预校验（问题 4）——推荐方案 A：WebView2 DevTools 协议受控注入

- **原理**：Tauri dev 构建启用 WebView2 DevTools；以测试环境变量 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<回环端口>` 启动 dev 应用，即可经 CDP（Chrome DevTools Protocol）在页面上下文执行既有 IPC：`window.__TAURI_INTERNALS__.invoke("create_import_entry", { path: "<测试路径>" })`（`awaitPromise`）；随后 `location.reload()` 触发前端挂载时的 `list_import_entries` 刷新（条目登记表在 **Rust 侧**，页面重载不丢失）→ UI 以正常渲染路径显示失败条目。
- **为何恰当**：① **零源码改动、零新依赖**（CDP 客户端用 Node 24 内建 `WebSocket`，本机已具备）；② 调用的就是**产品既有命令**（与对话框流程选中后调用的是同一个 `create_import_entry`），仅"路径来源"为测试注入——对"应用层失败处理与展示"的验证目标完全对应；③ **生产隔离可证明**：不设置该环境变量即无 CDP；Tauri release 构建默认不启用 devtools；全程无任何代码分支需要隔离；④ 不执行任意系统命令（唯一参数是测试路径字符串）。
- **待验证项（授权后首次执行时确认）**：该环境变量在本机 WebView2 版本下的实际生效性；若无效则切换备选 B。
- **备选 B（仅当 A 不可行；属代码变更，需单独授权）**：新增 `#[cfg(debug_assertions)]` 测试命令（如 `__test_create_entry`）——编译期隔离（release 构建不含该命令，可用 `cargo build --release` 后符号/字符串检索证明），capabilities 不需要变更；缺点是需要改 `lib.rs` 并新增一个源文件。
- **备选 C（不采用）**：在对话框 OK 后毫秒级竞态删除文件——非确定性，违背"稳定触发"要求。
- **明确排除**：拖拽导入、手动输入路径等**新增用户功能**（需求未要求；且超出"仅测试环境可用"约束）。

### 4.3 失败原因与状态展示的验证（问题 5）

用**同一时刻的单张截图**呈现失败条目（"导入失败"徽标 + `{message}（{code}）`）与成功条目（"已导入（路径校验通过）"）的对照；辅以 UIA 界面文本读取（同 Stage 2A 既有方法）与日志。

### 4.4 恢复证明（问题 6）

失败条目存在时，再经**真实对话框**成功导入一个文件（复用既已通过的 P2A-001 流程），观察：新条目正常出现、失败条目不干扰、窗口 `Responding=True`、无全局错误提示；随后关闭/重启窗口（Gate-2A 直接相关回归方法复用，不重复全套）。

### 4.5 测试安全边界（问题 7）

- 注入路径白名单：仅 `docs/evidence/stage2/test-assets/` 下的专用素材（脚本内硬编码校验，拒绝白名单外路径）。
- ACL 仅作用于 `acl-test-copy.mkv` 单文件，严格按 §10.2 执行并在结束时完成四验恢复。
- 不触碰用户源视频、真实 FFmpeg/FFprobe 安装、生产配置、系统 PATH/注册表；CDP 端口仅监听回环地址；测试结束关闭全部进程并核对无残留。
- 环境变量只存在于测试启动命令的作用域内（`tauri dev` 的启动进程），不写入系统或用户环境。
